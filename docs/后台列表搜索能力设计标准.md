# 后台列表搜索能力设计标准

> 用途：供后续 Agent 在分析后台页面、设计搜索能力和更新 PRD 时遵循。本文记录本项目已确认的原始判断逻辑与输出规范，不替代对实际页面的重新采集。

## 1. 核心目标

搜索能力的目标不是让每个列表字段都可搜索，而是帮助后台业务人员以最短路径完成高频的数据定位、问题排查和任务处理。

设计时必须回答：

1. 业务人员会因什么任务进入该页面？
2. 他们通常掌握哪些信息？
3. 哪些条件能显著缩小数据范围或唯一定位记录？
4. 哪些字段即使可筛选，也很少成为业务查询入口？

只有对业务任务有明确价值的字段才进入搜索方案。

## 2. 数据采集规则

### 2.1 必须重新读取实际页面

- 每分析一个模块，都要登录后台逐页核实。
- 记录实际菜单、页面表头、当前筛选器、详情页可见字段和页面状态。
- 不得依赖前一轮汇总、用户记忆或相邻页面字段推断。
- 同名或相似字段必须确认所属页面，避免跨页面错放。

### 2.2 事实优先

- 页面抓取结果与口头描述冲突时，重新核验页面，不得直接迎合任一方。
- “页面有字段”不等于“字段必须可搜索”。先确认事实，再做业务判断。
- 不得脑补页面不存在的数据能力，例如页面没有手机号时，不可在说明中加入手机号搜索。
- 动态枚举不得写死具体值或选项数量。

## 3. 搜索项选择原则

### 3.1 应优先支持的搜索项

通常包括：

- **唯一标识**：业务 ID、用户 ID、订单号、报告编号、反馈编号、卡号、设备 SN、OpenID 等。
- **高频用户线索**：姓名、昵称、手机号等业务人员通常能够获得的信息。
- **关键业务归属**：家庭 ID、机构 ID、渠道用户 ID、数据库及表等用于定位来源或归属的信息。
- **关键业务状态**：会直接影响待处理范围、异常排查或运营动作的状态。
- **关键时间范围**：注册时间、创建时间、检查时间等有明确时间段排查场景的字段。

### 3.2 不应默认加入的搜索项

- 仅因字段出现在表头就加入。
- 区分度低、业务查询价值弱的属性，如性别。
- 主要用于结果展示而不是记录定位的描述性内容，如病史描述。
- 无明确任务场景的时间字段，如用户管理中的最近登录。
- 家庭成员中的关系、出生日期、证件类型、证件号、身高、体重等，在当前业务场景下不作为常用查找入口。

### 3.3 合并与拆分规则

- **同一业务实体、同一操作意图**可合并为一个搜索框，例如“ID / 用户姓名”。
- **匹配方式明显不同且为高频入口**时应拆分，例如手机号使用精确匹配，应作为独立搜索项，不与姓名模糊搜索混在一起。
- 不同业务实体应拆分，例如家庭成员页的“主用户”与“成员”分别设计搜索项。
- 多个同类技术标识可在业务人员通常只掌握其中一个时共用搜索框，例如“平台用户ID / OpenID / UnionID”。

## 4. 搜索形式设计

### 4.1 关键词搜索

适用于 ID、姓名、手机号、编号、SN、OpenID 等文本字段。

- 唯一标识、手机号、编号：说明写“精确匹配”。
- 姓名、昵称等自然语言：说明写“模糊匹配”。
- 一个输入框支持多个字段时，说明必须分别写清每个字段的匹配方式，并注明“共用一个搜索框”。

### 4.2 下拉筛选

适用于有限枚举字段。

- 搜索形式栏只写“下拉筛选”。
- 单选或多选写在说明栏。
- **单选**：说明写“单选”。适合互斥且用户通常只需选择一个值的条件，如用户状态、第三方平台。
- **多选**：说明统一写“多选。所有+字段类型”，例如“多选。所有+病史类型”。
- 多选控件顶部必须有“所有”选项；下方每个动态选项带复选框。
- 点击“所有”表示不限条件，并清空其他勾选。
- 动态枚举只写“所有+类型”，不得列举具体值或数量。

### 4.3 日期范围选择器

适用于有明确按时间段定位业务记录的时间字段。

- 搜索形式栏写“日期范围选择器”。
- 不因列表存在时间字段就默认加入，必须有明确业务查询场景。

## 5. PRD 记录格式

每个页面先记录实际页面表头，再记录搜索方案：

```markdown
##### 页面名称

页面表头：字段A、字段B、字段C

| 搜索项 | 搜索形式 | 说明 |
|-|-|-|
| ID / 姓名 | 关键词搜索 | ID 精确匹配；姓名模糊匹配，共用一个搜索框 |
| 手机号 | 关键词搜索 | 精确匹配 |
| 状态 | 下拉筛选 | 单选 |
| 类型 | 下拉筛选 | 多选。所有+类型 |
| 创建时间 | 日期范围选择器 |  |
```

记录规范：

- 表头名称使用“搜索项”，不用“列名”。
- “搜索形式”只记录组件类型：关键词搜索、下拉筛选、日期范围选择器。
- 精确/模糊、单选/多选全部写在“说明”。
- 不写“已有”“新增”“保留”“现状支持”等历史状态。
- 不写动态选项的具体枚举或数量。
- 不把当前页面不存在的字段写进搜索项或说明。

## 6. 已确认的页面决策样例

### 6.1 健康史

- ID 与用户姓名可共用一个关键词搜索框。
- 病史描述不作为搜索项。
- 病史类型使用下拉筛选，说明为“多选。所有+病史类型”。

### 6.2 用户管理

- ID、姓名、昵称共用关键词搜索框。
- 手机号作为独立搜索项，精确匹配。
- 性别不作为筛选项。
- 状态为单选。
- 最近登录不作为搜索项。
- 注册时间可作为日期范围搜索项。

### 6.3 渠道用户

- 沿用用户管理的实体搜索逻辑：ID/用户名共用，手机号独立。
- 渠道用户 ID、机构 ID作为精确定位项。

### 6.4 家庭成员

只保留直接定位主用户和成员的信息：

- 主信息：ID / 用户姓名、用户手机号。
- 成员信息：成员姓名、成员手机号。
- 关系、性别、出生日期、证件类型、证件号、身高、体重均不作为搜索项。

### 6.5 反馈管理

当前方案已确认，可围绕反馈编号、来源、设备 SN、用户、状态、创建时间、更新时间进行搜索和筛选。

## 7. Agent 执行流程

1. 获取目标模块的真实菜单与页面 URL。
2. 逐页抓取表头、筛选器和必要的详情字段。
3. 先输出事实清单，不跨页面混用字段。
4. 从业务任务出发筛除低价值搜索项。
5. 判断关键词搜索、下拉筛选或日期范围选择器。
6. 决定字段合并或拆分，并写清匹配方式。
7. 按统一表格格式写入 PRD。
8. 写入后重新读取目标章节，逐项核验。

## 8. 提交前自检清单

- [ ] 页面表头是否来自本次实际采集？
- [ ] 是否把其他页面的字段错放到本页面？
- [ ] 是否存在页面中没有但说明里出现的字段？
- [ ] 每个搜索项是否有明确业务使用场景？
- [ ] 是否误把性别、描述性字段等低价值字段一股脑加入？
- [ ] 手机号等高频精确线索是否独立设计？
- [ ] 搜索形式栏是否只写组件类型？
- [ ] 精确/模糊、单选/多选是否只写在说明栏？
- [ ] 多选是否写成“多选。所有+类型”？
- [ ] 是否避免列举动态枚举和值数量？
- [ ] 是否避免“已有/新增/保留”等历史表述？
- [ ] 写入飞书后是否重新读取并核验？
